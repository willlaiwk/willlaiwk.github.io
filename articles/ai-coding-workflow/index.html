讓 AI 成為開發夥伴：不把大腦外包的 Coding Agent 實戰流程

當 AI 幾秒鐘就能產出程式碼，開發的瓶頸已經轉移到「人」。分享我從大型專案重構踩坑後，建立的規格先行、Session 切分與跨模型審查流程。

W.
Will2026.10.18 8 分鐘閱讀

當 AI 可以在幾秒鐘內產出幾百行程式碼，軟體開發的瓶頸其實已經轉移了。現在真正卡住團隊的，往往不是「寫不出來」，而是「人」——我們對系統的理解、做技術決策的速度、審查程式碼的方式，甚至是團隊既有的文化與流程。

這篇筆記想分享我在日常產品開發中，與 Coding Agent 協作的真實體悟：為什麼我們不能把大腦外包給 AI，以及我如何透過「規格先行、Session 切分、跨模型審查與證據交付」，建立一套真正可控的開發流程。

沒有領域理解與規格邊界，連 AI 的提問都接不住

很多人以為遇到不熟悉的大型專案，正好可以交給 AI 幫忙重構。但我近期剛加入新公司、接手一個大型專案的部分重構時，卻狠狠踩了一個坑。

當時在缺乏文件、自己也還不熟悉整體業務脈絡、現有架構與各模組相依性的情況下，我很難在一開始就定義出精準的規格與任務邊界。那時我想：「沒關係，先請 Agent 幫我探索並產生重構計畫。」

結果在討論過程中，即使 Agent 主動提出了很多關鍵問題與選項，我卻因為對專案的業務與底層相依性不夠了解，根本無法做出好的判斷與回答。更糟的是，在沒有明確規格與驗收條件（AC）的狀態下邊做邊改，對話的 Context 越滾越大，Agent 開始發散、甚至遺忘最前面的決策，最終導致重構方向過於龐大且發散，幾乎難以收斂。

這次經驗讓我非常確定兩件事：

  1. AI 無法替你補齊「領域認知」：當工程師對業務領域（Domain）或技術底層理解不足時，就算 Agent 會提問，你也接不住。在動手改架構前，人必須先搞懂系統邊界與相依性。
  2. 沒有規格書就開工，長 Context 必然失控：不先把邊界釘死，Agent 只會在錯誤或過大的方向上加速狂奔。

清楚的規格與上下文不是附加資訊，而是防止 Agent 在長對話中迷航的錨點。

從「邊做邊聊」改為「規格先行、一階段一 Session」

現在動工前，我一定會先把任務目標與足夠的上下文素材提供給 Agent，透過來回討論先收斂出兩份產出，才允許寫程式：

  • 規格書（Spec）：明確寫下 Why（為什麼做）、What（做什麼）、Scope（In Scope / Out of Scope，明確界定這次做什麼、不做什麼）、How（架構與技術思路）以及 AC（驗收條件）。
  • 任務清單（Phases → Tasks）：如果是較大的改動，會先拆成多個階段（Phases），每個階段底下再拆出具體的子任務（Tasks）。

一份動工前的規格與階段拆解範例

以下是一個簡化版的骨架範例，用來示意每個區塊涵蓋的方向（實際專案中的 Spec 會包含更完整的資料結構、流程細節與邊界定義，不會只有短短一兩句話）：

[Spec 摘要（簡化示意）]
- Why：既有模組耦合度過高，修改單一流程容易影響其他業務邏輯
- What：抽離共用狀態與資料流，保持對外介面與既有行為不變
- Scope：
  - In Scope：核心狀態模組抽離、既有呼叫端替換、對應單元測試補齊
  - Out of Scope：不修改 API 回傳格式、不調整 UI 視覺樣式、不順手重構周邊無關模組
- How：先補齊關鍵邊界驗證，再分階段替換內部實作，不一次重寫全部模組
- AC：既有功能與邊界情境行為一致、通過型別與測試檢查、附上改動前後對照證據

[任務清單（Phases → Tasks）]
- Phase 1：梳理相依性、建立共用介面與基礎驗證
  - Task 1：盤點既有模組相依處，補齊關鍵流程的邊界測試
  - Task 2：定義新的共用狀態介面與型別
- Phase 2：遷移核心模組並替換舊有呼叫端
  - Task 1：實作新的狀態管理邏輯並通過單元測試
  - Task 2：逐步替換既有元件的呼叫端，確認行為一致
- Phase 3：清理廢棄程式碼與執行最終整合驗證
  - Task 1：移除舊有耦合邏輯與不再使用的相依程式碼
  - Task 2：執行完整檢查並整理改動前後的對照 Evidence

在進入實作時，我會根據任務的數量與大小，決定要切分多少個 Session 來處理——原則上是 「1 個 Phase 開 1 個獨立的 Session」。

階段 工程師的責任 Coding Agent 的角色
對齊與規格 提供業務背景、釐清模組相依性、界定 In / Out of Scope、拍板決策 協助梳理脈絡、點出盲點、產出 Spec（Why/What/Scope/How/AC）
任務拆解 決定階段邊界與交付粒度 將 Spec 拆解為 Phases -> Tasks 清單
分階段實作 控制 Session 邊界（1 Phase = 1 Session） 在乾淨的 Context 中專注完成單一 Phase

這樣做的好處是每個 Session 的 Context 都能保持乾淨、聚焦，不會因為對話過長而開始「失憶」或推翻前面的架構決策。

跨模型唯讀審查，與「帶證據」的交付

當 AI 完成一個較大的任務、改動了大量程式碼時，要求工程師用肉眼一行一行做 Code Review 其實很不切實際——人眼容易疲勞，也很難在幾百行語法細節裡維持高品質的判斷。

為了讓審查真正有效，我現在在送出 PR / MR 之前，會加入兩道關卡：

1. 用兩個不同模型的 Agent 做「唯讀 Code Review」

實作完成後，我會根據事先定義好的 Review 規範，指派與實作模型不同的另外 2 個 Agent 同時進行 Code Review。這裡有兩個關鍵原則：

  • Review Agent 只負責審查，不直接修改程式碼：把「挑錯」與「修改」的職責分離，避免審查者在沒對齊的情況下又把程式改壞。
  • 雙模型交叉審查：單一模型往往有固定的思考盲點或偏好，同時讓兩個不同模型的 Agent 平行審查，能涵蓋更完整的問題面向（例如一邊抓出邊界條件遺漏，另一邊抓出架構相依性問題）。

2. 測試綠燈還不夠，必須附上 Evidence

「編譯過了、測試跑通了」不代表真的做對了。在全部任務完成後，我會要求 Agent 附上具體的驗證證據（Evidence），例如修改前後的畫面對照截圖、實際操作錄影，或是關鍵流程的驗證輸出。

直到跨模型 Review 的問題收斂、證據也齊全後，我才會正式送出 PR / MR。而在 PR Description 中，我也會整理成「方便人類 Reviewer 做決策」的結構：

1. Summary：這次改動的一句話摘要
2. Why / What / How：為什麼做、改了什麼、背後的架構與思路
3. Validation & Evidence：驗證結果、修改前後對照截圖或影片
4. Risk & Rollback：可能對既有系統產生的影響範圍與風險、若出問題如何快速回退
5. Open Questions：需要 Reviewer 一起決議或確認的取捨
6. Review Guide：建議 Reviewer 的閱讀重點與查看順序

這樣組織 PR Description 的好處，是能大幅降低 Reviewer 的認知負擔——讓團隊不必在幾百行程式碼差異裡拼湊改動意圖，而是透過完整的脈絡、驗證證據與閱讀順序，直接把精力放在真正的架構判斷與決策上。

當「人」成為最大瓶頸：別把大腦外包給 AI

走過這段從踩坑到建立流程的過程，我對「人與 AI 協作」最大的體悟是：AI 雖然大幅加速了開發與寫作，但「人」卻成了目前最大的瓶頸。

這個瓶頸體現在做決策的速度、Code Review 的消化能力，甚至是公司的文化與協作流程。尤其在當前的 AI 時代，很多人習慣把大腦外包給 Agent——不看規格、不深究業務與技術細節，久而久之漸漸失去獨立判斷的能力，最後只能盲目地按下 Accept，照單全收 Agent 的建議。

AI 可以幫我們寫程式、跑測試、甚至交叉檢查錯誤；但理解系統、定義問題邊界，以及為最終的技術決策負責，始終是工程師無法外包的核心價值。
